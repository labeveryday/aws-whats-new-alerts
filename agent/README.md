# AWS Newsletter Agent

A fully autonomous AI agent built with AWS Bedrock AgentCore and Strands that generates and delivers daily email newsletters about AWS AI/ML announcements.

## Overview

This agent:
- **Fetches** AWS news from https://aws.amazon.com/new/
- **Filters** for AI/ML-related content (or broader coverage on request)
- **Deduplicates** using AgentCore semantic memory
- **Formats** professional ASCII-bordered newsletters with numbered announcements
- **Delivers** via Amazon SNS email subscriptions

## Deployment

### 1. Configure Agent
```bash
cd agent
agentcore configure -e agent.py
```

### 2. Deploy to AgentCore
```bash
agentcore launch
```

Copy the agent ARN from output and add to `.env`:
```bash
echo "AGENTCORE_ARN=arn:aws:bedrock-agentcore:..." >> ../.env
```

### 3. Enable Autonomous Operation (Optional)
```bash
cd ../backend
cdk deploy --context email=your-email@example.com \
           --context agentcore_arn=<your-agent-arn> \
           --context enable_scheduler=true
```

This deploys EventBridge Scheduler to trigger the agent daily at 6 AM EST.

## Agent Capabilities

### Tools
- **http_request** (Strands built-in) - Fetches AWS news feed
- **current_time** (Strands built-in) - Gets current date
- **publish_message** (custom, auto-loaded from `tools/sns_tools.py`) - Sends emails via SNS
- **subscribe_email** (custom) - Manages SNS subscriptions

### Memory Integration
- **Namespace**: `/newsletter/facts` (storage) and `/newsletter/articles`
- **Strategy**: Semantic extraction with custom prompt
- **Query**: On session start, retrieves previously processed article URLs
- **Extraction**: Automatically extracts URLs mentioned in agent responses
- **Expiry**: 30 days (configurable in CDK stack)

### Deduplication Logic
1. Agent starts → Memory queried for processed article URLs
2. Fetch AWS news → Extract all article URLs
3. Cross-reference with memory → Identify NEW vs ALREADY PROCESSED
4. Create newsletter with only NEW articles
5. Mention processed URLs in response → Memory extracts for future deduplication

## Troubleshooting

### Agent Not Creating Memory Records
**Symptom**: Day 2 doesn't skip duplicates from Day 1

**Causes**:
1. Agent not mentioning article URLs in response
2. Semantic extraction prompt not configured in CDK
3. Memory provisioning incomplete (wait 5min after CDK deploy)

**Fix**:
```bash
# Verify CDK has custom_extraction configured
cd backend
cat newsletter_stack.py | grep -A 5 "custom_extraction"

# Should see:
# custom_extraction=agentcore.OverrideConfig(
#     append_to_prompt="Extract facts for AWS article deduplication..."
# )
```

### Namespace Mismatch
**Symptom**: Agent queries memory but gets no results

**Causes**: Agent retrieval_config namespaces don't match CDK strategy namespaces

**Verify**:
```bash
# CDK namespaces (should be /newsletter/facts)
grep "namespaces=" backend/newsletter_stack.py

# Agent retrieval_config (should match)
grep "retrieval_config=" agent/agent.py -A 10
```

### Memory Not Found Error
**Symptom**: "Memory not found" on agent invocation

**Causes**: Memory still provisioning (takes 2-5 minutes after CDK deploy)

**Fix**: Wait 5 minutes, then redeploy agent

### Email Not Received
**Symptom**: Agent runs successfully but no email arrives

**Causes**:
1. SNS subscription not confirmed (check email for confirmation link)
2. SNS topic ARN not in .env
3. IAM role lacks SNS publish permissions

**Fix**:
```bash
# Check SNS subscription status
aws sns list-subscriptions-by-topic \
    --topic-arn $SNS_TOPIC_ARN \
    --region us-east-1

# Should show: "SubscriptionArn": "arn:..." (not "PendingConfirmation")
```

## Memory Strategy Details

### CDK Configuration (backend/newsletter_stack.py)
```python
agentcore.MemoryStrategy.using_semantic(
    name="newsletter_facts",
    namespaces=["/newsletter/facts", "/newsletter/articles"],
    custom_extraction=agentcore.OverrideConfig(
        append_to_prompt=(
            "Extract facts for AWS article deduplication:\n"
            "- Article URL (unique key for deduplication)\n"
            "- Article title\n"
            "- Publication date\n"
            "- Processing timestamp (when included in newsletter)\n"
            "Enable querying: 'Which article URLs have been processed?' to prevent duplicates."
        )
    )
)
```

### Agent Configuration (agent.py)
```python
retrieval_config={
    "/newsletter/facts": RetrievalConfig(
        top_k=50,
        relevance_score=0.8,
        initialization_query="What AWS articles have been processed in recent newsletters? List all article URLs."
    ),
    "/newsletter/articles": RetrievalConfig(
        top_k=20,
        relevance_score=0.7
    )
}
```

### How It Works
1. **Session Start**: Strands session manager queries `/newsletter/facts` with initialization_query
2. **Context Injection**: Memory results injected as assistant messages before user prompt
3. **Agent Processing**: Agent sees "Previously processed: [url1, url2, ...]" in context
4. **Deduplication**: Agent filters out any URLs found in memory
5. **Response**: Agent mentions new URLs: "Processed [url3, url4]"
6. **Extraction**: Semantic strategy extracts URLs from agent response
7. **Storage**: New URLs stored in `/newsletter/facts` for next invocation

## Design Decisions

### Why No Lazy Loading?
AgentCore Runtime reuses Python processes across invocations. A lazy-loaded singleton would share the same `session_id` across all invocations, breaking memory isolation. Instead, we create a fresh agent instance per invocation.

### Why AgentCore-Managed Session IDs?
Custom session IDs (e.g., `aws-newsletter-2025-11-05`) would create one session per day. All invocations that day would share the same session, leading to context pollution. Using `context.session_id` ensures proper isolation.

### Why Semantic Strategy?
Built-in semantic extraction automatically captures facts from natural conversation without requiring explicit storage code. The agent simply mentions URLs in its response, and the strategy handles extraction and persistence.

### Why /newsletter/facts Namespace?
Global namespace (not actor-specific) because:
1. Single bot deployment (no multi-tenancy needed)
2. Simpler configuration (no placeholder variables)
3. Easier testing and debugging
4. Shared deduplication state across all invocations

## Performance

- **Cold start**: ~3-5 seconds (AgentCore container initialization)
- **Warm invocation**: ~1-2 seconds (process reuse)
- **Memory query**: <500ms (top_k=50 from semantic index)
- **AWS news fetch**: ~1-2 seconds (http_request to aws.amazon.com/new)
- **Newsletter generation**: ~5-10 seconds (Claude processing)
- **Total execution**: ~10-15 seconds per newsletter

## Security

- **Least privilege IAM**: AgentCore Runtime role has minimal permissions (SNS publish only)
- **Memory isolation**: Actor-level (via actor_id) and session-level (via session_id)
- **No credentials in code**: All secrets from environment variables or IAM roles
- **CloudWatch logging**: All executions logged for audit trail

## Cost Estimation

**Daily operation (1 newsletter/day):**
- AgentCore Runtime invocations: ~$0.01/day
- Bedrock Claude (Sonnet): ~$0.05-0.10/day (depends on article count)
- AgentCore Memory storage: ~$0.01/day
- SNS: First 1,000 emails/month free, then $2/100,000
- CloudWatch Logs: Negligible (<1MB/day)

**Estimated total**: ~$2-3/month for daily newsletter
